# Research brief schema

Research briefs come from the player's Gemini Gem ("Fretwork Coach: Curriculum Architect"). They arrive in Google Drive at `FretworkCoach/Briefs/Inbox`. One long reply gets cut off, so **a brief arrives in five parts**, one JSON file each: `[topicId].core.json`, `[topicId].foundations.json`, `[topicId].intermediate.json`, `[topicId].advanced.json`, `[topicId].mastery.json`. (A single `[topicId].json` in the full shape below is still accepted.) The scheduled content run fetches the files itself, assembles them with `node content/briefs/merge-brief.mjs <folder> <topicId>`, builds the topic from the merged brief instead of re-researching it, then copies the files to `FretworkCoach/Briefs/Processed`. A topic with a missing or invalid part is not built; the summary says which part is missing.

A brief is research, not finished content. The app's lessons are generated by code in all 12 keys, so a brief supplies the teaching sequence, the facts and exact pattern rules; the run turns them into generators.

## The five parts

- **core**: `schemaVersion`, `topic`, `pedagogy`, `concept` (facts and every pattern), `guardrails`, `openQuestions`. No `tiers`. Small.
- **tier part** (`foundations`, `intermediate`, `advanced`, `mastery`): `{ "schemaVersion": 1, "topicId": "", "tier": "foundations", "goal": "", "skills": [ ... ], "openQuestions": [] }`. Skills and lessons have the shape shown below. Lessons may only cite `patternId`s that exist in the core; a tier part that cites an unknown pattern is rejected. Depth per tier follows CONTENT.md's reference standard (Foundations 4+ skills / 8+ lessons, Intermediate 4+ / 10+, Advanced 4+ / 8+, Mastery 3+ / 6+).
- `merge-brief.mjs` puts each tier part's `goal` and `skills` into `tiers.<tier>`, concatenates `openQuestions`, checks parts, ids and patternIds, and prints the full brief (or the problems).

## Shape of the merged brief (strict JSON)

```json
{
  "schemaVersion": 1,
  "topic": { "id": "camelCase", "title": "", "kind": "technique|subject|style", "domain": "fretting|picking|rhythm|fretboard|theory|ear|improv", "prereqs": [], "summary": "" },
  "pedagogy": {
    "date": "YYYY-MM-DD", "summary": "",
    "sequence": [ { "id": "", "tier": "foundations|intermediate|advanced|mastery", "step": "", "how": "", "source": 0 } ],
    "drills": [], "mistakes": [],
    "sources": [ { "title": "", "author": "", "url": "", "type": "primary|secondary" } ]
  },
  "concept": {
    "facts": [],
    "patterns": [ {
      "id": "", "name": "",
      "notation": [[string, fret]],
      "loop": true,
      "referencePosition": "",
      "notesPerString": {}, "stringOrder": [],
      "picking": { "mode": "", "firstStroke": "d|u", "stringChanges": "inside|outside|mixed" },
      "fingering": "", "fingeringConfirmed": false,
      "variants": [], "movement": "",
      "confirmed": "player|primary|secondary|unconfirmed",
      "sources": [0]
    } ]
  },
  "tiers": {
    "foundations": { "goal": "", "skills": [ { "id": "", "title": "", "domain": "", "focus": "",
      "lessons": [ { "id": "", "name": "", "patternId": "", "unit": "", "baseGoalBpm": 100, "minutes": 5, "method": "", "pass": "" } ] } ] },
    "intermediate": {}, "advanced": {}, "mastery": {}
  },
  "guardrails": [],
  "openQuestions": []
}
```

Conventions: strings are numbered 1 = high e to 6 = low E; frets 0-22; standard tuning unless stated. `baseGoalBpm` is roughly the goal tempo for a level-4 player (the app scales it by level).

## Lean briefs (since 2026-10-14)

The Gem supplies research and structure only: skills have a one-sentence `focus` and lessons have a measurable `pass`; there is no `study`, `why`, `instr`, `watch` or `simplify`. The build writes all lesson prose itself, **only from the brief's patterns, facts, pedagogy sequence and guardrails**. Anything the prose assumes beyond them is listed in the run summary under "Needs your check". Older full briefs that still carry those fields are accepted; treat their prose as a draft to verify, not as fact.

Gemini's sources are leads, not proof. A source with url `unverified`, a `primary` source the build cannot confirm, or `fingeringConfirmed: true` with nothing behind it is treated as `unconfirmed` until the player says otherwise. When a topic's patterns come from a player specification in `content/QUEUE.md`, the build checks the brief's `player` patterns against that row's exact strings, frets and picking and stops if they differ.

## How the parts reach Drive

Each reply is exported from Gemini with "Export to Docs" (this makes a Google Doc in My Drive root), then found in Drive by creation time, renamed to `[topicId].core.json` (or `.foundations.json` etc.) and moved to `Briefs/Inbox`. The Doc text may carry Markdown escapes (`\[`); `merge-brief.mjs` undoes them.

## Rules for the build

- `confirmed: "player"` is final. Never override it or re-check it against other sources.
- `player` is only valid when the topic's row in `content/QUEUE.md` (Player requests) contains an explicit specification with exact strings, frets and picking, and the brief's pattern matches it exactly. The Gem has been seen marking its own invented patterns `player` (thumping, 2026-10-15), so a `player` pattern with no matching specification in the row is treated as `unconfirmed`, and a mismatch builds nothing. Topics from the Discovered section have no player specification, so none of their patterns may be `player`.
- Strings 7 and 8 are not supported by the app yet (see REQUESTS); a brief with notation on string 7 or 8 is rejected by `merge-brief.mjs`.
- Artist-named patterns are built only from exact strings, frets and picking in the brief. Anything `unconfirmed` or missing goes in the run summary under "Needs your check".
- A malformed brief, or one missing context needed to build correctly, builds nothing; the summary says what is missing.
- Exercises stay original ("in the style of"); never transcribe a riff, solo or tab.
- Do not combine tasks the sources do not combine.
